# v0.6.6 启动迁移容量故障

状态日期：2026-09-06。修复已纳入 v0.6.7 定版源码；签名发布以独立发布证据为准，本机更新由用户操作。

## 现象与根因

本机从旧版升级到签名的 v0.6.6 后，在启动阶段退出。已安装包版本为 0.6.6，`codesign --verify --deep --strict` 通过。系统崩溃报告显示 Rust setup 回调触发 abort；直接捕获启动 stderr 后确认首个错误为“执行 SQLite migration 14 失败”。

只读检查原库：迁移版本 13，121,108 页，每页 4,096 bytes，共 496,058,368 bytes（约 473 MiB），没有空闲页。将原库通过 SQLite backup API 复制到仓库外的私有目录，在副本上以原 131,072 页上限执行迁移 14，复现 `SQLITE_FULL`。迁移事务回滚，没有登记版本 14。给副本足够空间后，新增索引使页数达到 134,546（约 526 MiB），因此超过旧 512 MiB 程序预算；副本 `quick_check` 为 `ok`。这不是签名校验失败，也不能据此判断用户物理磁盘已满。

## 修复

SQLite 主数据库预算改为固定 1 GiB，使用实际 `page_size` 计算 `max_page_count`。预算不会随每次打开自动增加；WAL、临时索引文件等不在 SQLite 主数据库页预算之内。没有修改迁移 SQL、清空数据库、删除历史活动或修改 Codex 配置及认证资料。

## 验证

- `cargo test --offline -p codex-storage`：19 项通过，其中 3 项新增容量回归覆盖：受限迁移失败的事务回滚、同一人工旧库重试成功及重复打开、checkpoint 和旧记录保留、1/4/8 KiB 页大小、固定预算、写满后无部分记录。
- `npm test`：125 项通过。
- `cargo fmt --all -- --check`、存储 crate 全 target Clippy 通过；文档离线检查通过（33 份文档、15 个版本说明、143 个链接）。
- 生产 `Store::open` 对原始 v13 库的另一份私有副本执行迁移成功。迁移后版本 14、134,546 页，14 张已有业务表的行数及全部 ingest checkpoint 保持一致，`quick_check=ok`。
- 原始数据库仍处于迁移 13，未把副本回写原库，未替换本机安装包。诊断期间仅重现启动失败，没有业务请求或配置切换。

## 状态与限制

`implemented` 与上述 `tested` 已完成；v0.6.7 已完成签名发布及公开资产复验，见[发布证据](release-v0.6.7.md)。安装后的真实启动 `accepted` 仍待用户自行更新后验证。此次发现说明之前小规模人工升级 fixture 与签名/公证验证未覆盖接近旧容量上限的真实数据库；以前的公开资产验证成功不等于这条升级启动链通过。

固定 1 GiB 仍是有限预算，真实磁盘不足、数据库损坏或达到新上限仍可能导致启动/写入失败；本切片不改写 Tauri 的通用启动异常处理。不得把增加容量描述为永久消除所有 `SQLITE_FULL` 情况。

修复源码可回退；真实数据库尚未迁移，因此不需要对用户数据库执行回滚。私有数据库副本只用于本次验证，不进入仓库或发布资产，验证完成后已清理。原有 `design-qa.md` 保持不变。`deployment_decision=project-authorized`：诊断及本地验证完成后，用户明确授权提交、推送和发布 v0.6.7，并要求本机更新由用户自己操作。
